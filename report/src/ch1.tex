\chapter{Introduction}

In recent years, the adoption of Kubernetes and container technologies has surged due to their versatility and scalability for the deployment of massive and highly-available distributed applications. Securing these complex environments at various levels is imperative. In this lab, we delve into the critical issue of runtime security monitoring, exploring solutions for securing Kubernetes clusters and enforcing threat detection mechanisms in real-time. These measures are necessary to provide visibility and observability for containerized applications in such dynamic computing environments.

While the isolation between containers restricts the impact of an exploited application, several runtime threats can still manifest. Through hands-on exercises, students will gain a deep understanding of runtime security mechanisms, their significance in mitigating security risks, and practical implementation techniques to fortify Kubernetes deployments against emerging threats.

From a security perspective, containers are exposed to different attack vectors aiming to breach the security boundary and escape container isolation, potentially performing lateral movements within the system and escalating privileges. This vulnerability is particularly concerning in multi-tenant environments where different users run their workloads on a shared hardware.

One of the most widely adopted security tools for container runtime security is \textbf{Falco}, an open-source cloud-native runtime security project. It acts as a security camera detecting unexpected behavior, intrusions, and data theft in real-time. In this lab, students will practice deploying a vulnerable application, monitoring its behavior with Falco, and ultimately simulating an attack to observe how a command injection can lead to a reverse shell. 

All the exercises will be carried out by using Virtual Machines on CrownLabs, running all the necessary tools for creating the Kubernetes cluster and experimenting with it.

\chapter{Initial Setup}

The physical setup of this lab consists of two VMs representing our bare-metal infrastructure. The first VM will act as the Kubernetes \textit{control plane}, while the second will act as the \textit{worker node}. The installation process requires the \texttt{kubeadm}, \texttt{kubectl}, and \texttt{kubelet} packages to be installed on all servers: the provided CrownLabs image already includes them.

\section{Configuring the Kubernetes Cluster with kubeadm}

The Kubernetes control plane, including components such as the API server and the controller manager, governs the cluster behavior. Specifically, the control plane maintains a record of all the Kubernetes objects in the system and runs continuous control loops to manage those objects' state. 

\subsection{Configuring the control plane node}

First, select a VM that is supposed to act as the control plane node and change the name of the machine to clarify its function in the Kubernetes cluster:

\begin{lstlisting}[language=bash]
sudo hostnamectl set-hostname control-plane-1
\end{lstlisting}

\textbf{Warning}: you have to disconnect from the VM and open another SSH session to update the prompt. Then, from the same node, it is possible to leverage \texttt{kubeadm} to initialize the control-plane:

\begin{lstlisting}[language=bash]
sudo kubeadm init --pod-network-cidr=10.254.0.0/16 --service-cidr=10.255.0.0/16
\end{lstlisting}

\texttt{kubeadm init} first runs a series of pre-flight checks to ensure that the machine is ready to run Kubernetes, then downloads and installs the cluster control plane components. This may take several minutes. As part of the installation process, the previous command will print on screen a join string. \textbf{Take note of it}, because it will be required later in the installation process of the worker.

Once the configuration completed, it is possible to make \texttt{kubectl} work for the current user:

\begin{lstlisting}[language=bash]
mkdir -p $HOME/.kube
sudo cp /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config
\end{lstlisting}

Kubernetes does not embed the logic to interconnect different pods. Instead, it leverages a modular architecture based on the Container Network Interface (CNI). In this lab, we select \textbf{Cilium}, an open-source solution which provides highly scalable networking and security capabilities based on eBPF (Extended Berkeley Packet Filter).

\begin{tcolorbox}[colback=blue!5!white,colframe=blue!75!black,title=Why Cilium and Falco together?]
Both Cilium and Falco exploit the power of \textbf{eBPF}, a revolutionary Linux kernel technology that allows safe, sandboxed programs to run inside the OS kernel without modifying its source code or loading kernel modules. However, the two tools operate at complementary layers of the security stack:
\begin{itemize}
    \item \textbf{Cilium} leverages eBPF for \textit{network security}: it enforces Network Policies at layers L3/L4/L7, provides load balancing, and secures east-west traffic between pods. Without a CNI like Cilium, pods cannot communicate at all.
    \item \textbf{Falco} leverages eBPF for \textit{runtime security}: it intercepts Linux system calls made by containerized processes directly from the kernel, detecting anomalous behaviors such as spawning shells, reading sensitive files, or opening unexpected network connections.
\end{itemize}
Together, they represent two fundamental and complementary pillars of cloud-native security: Cilium controls \textit{what can be reached}, while Falco detects \textit{what is happening at runtime}.
\end{tcolorbox}

Cilium can be installed through the provided CLI:

\begin{lstlisting}[language=bash]
curl -L --remote-name-all https://github.com/cilium/cilium-cli/releases/latest/download/cilium-linux-amd64.tar.gz
sudo tar xzvfC cilium-linux-amd64.tar.gz /usr/local/bin
rm cilium-linux-amd64.tar.gz
cilium install --version 1.15.14
\end{lstlisting}

Once Cilium is installed, wait for it to report that the cluster is healthy:

\begin{lstlisting}[language=bash]
cilium status --wait
\end{lstlisting}

\subsection{Configuring the worker node}

When the control plane node is ready, access the other VM to join it to the cluster as a worker node. Change its hostname for easier identification (remember to close and reopen the SSH session to update the prompt):

\begin{lstlisting}[language=bash]
sudo hostnamectl set-hostname worker-1
\end{lstlisting}

Then, run the \texttt{kubeadm join} command echoed during the control plane setup process. The command should be similar to the following (remember to prepend \texttt{sudo}):

\begin{lstlisting}[language=bash]
sudo kubeadm join 172.16.183.32:6443 --token <your-token> \
  --discovery-token-ca-cert-hash sha256:<your-hash>
\end{lstlisting}

Then, move back to the control plane and check that all nodes are correctly ready:

\begin{lstlisting}[language=bash]
kubectl get nodes -o wide
\end{lstlisting}


\section{Deploying the Vulnerable Application}

Now that you have a fully working Kubernetes cluster, we can proceed to deploy the environment required for the security monitoring activities.

We will use a sample web application called \texttt{zipapp}. This application allows users to upload a ZIP file and extracts it. However, it is vulnerable to Command Injection due to insecure usage of the Linux \texttt{unzip} command. Such vulnerabilities are surprisingly common in legacy codebases and represent a perfect entry point for malicious actors.



The instructor has provided a ZIP archive containing all the necessary materials for this lab (manifests, payloads, and profiles). Extract the archive and navigate to the manifests directory:

\begin{lstlisting}[language=bash]
unzip material.zip
cd material/manifests
\end{lstlisting}

Deploy the application in the \texttt{default} namespace:

\begin{lstlisting}[language=bash]
kubectl apply -f zipapp-deployment.yaml
kubectl apply -f zipapp-service.yaml
\end{lstlisting}

Verify that the application is running:

\begin{lstlisting}[language=bash]
kubectl get pods
\end{lstlisting}

The output should show the \texttt{zipapp} pod in the \texttt{Running} state:
\begin{lstlisting}[language=bash]
NAME                      READY   STATUS    RESTARTS   AGE
zipapp-5ffd444d74-jbwq2   1/1     Running   0          45s
\end{lstlisting}


\section{Installing Falco via Helm}

Falco is a CNCF graduated project for runtime security. It parses Linux system calls from the kernel at runtime, and asserts the stream against a powerful rules engine. 

To install Falco in our Kubernetes cluster, we will use Helm. 

Add the Falco repository to Helm:

\begin{lstlisting}[language=bash]
helm repo add falcosecurity https://falcosecurity.github.io/charts
helm repo update
\end{lstlisting}

Now install Falco in a dedicated namespace (\texttt{falco}). We will use the \texttt{modern\_ebpf} driver, which is the recommended way to collect system calls on modern Linux kernels.

\begin{lstlisting}[language=bash]
helm install falco falcosecurity/falco \
  --namespace falco \
  --create-namespace \
  --set tty=true \
  --set driver.kind=modern_ebpf
\end{lstlisting}

Wait a few seconds, then verify that the Falco daemonset has been successfully deployed and the pods are running:

\begin{lstlisting}[language=bash]
kubectl get pods -n falco
\end{lstlisting}

\begin{lstlisting}[language=bash]
NAME          READY   STATUS    RESTARTS   AGE
falco-4dgzk   2/2     Running   0          39s
\end{lstlisting}

Falco is now silently monitoring all the system calls in our cluster!
